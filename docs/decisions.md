# BookBook — Bookworm on an ESP32-S3

## Goal

A stand-alone, single-button Bookworm: press the button, speak, hear the reply. No PC. It mirrors the behaviour of [Bookworm](../../Bookworm/docs/decisions.md) (voice librarian for a Vision Australia Library member's account: search, bookshelf, request list, subscriptions, reading-preference memory, discovery conversation) on a Waveshare ESP32-S3-AUDIO-Board.

The end user is the same person Bookworm was built for: vision-impaired, single-button interaction, nothing visual to rely on. Every state must be audible.

## Hardware (Waveshare ESP32-S3-AUDIO-Board)

- ESP32-S3R8: dual-core 240 MHz, 512 KB SRAM, **8 MB octal PSRAM**, **16 MB flash**, Wi-Fi + BLE
- ES7210 (4-ch ADC, mic input) with dual digital mic array; ES8311 (DAC/codec) + speaker amp, MX speaker connector
- TCA9555 I2C GPIO expander (likely gates amp enable / buttons / LEDs — confirm from schematic v1.1)
- 7 RGB LEDs, BOOT / RESET / one user button, microSD slot, PCF85063 RTC, battery charging
- USB-C power + programming

Resources: https://docs.waveshare.com/ESP32-S3-AUDIO-Board/Resources-And-Documents (schematic v1.1, demo package, ES8311/ES7210 datasheets).
Pin maps (I2S, I2C, expander bit assignments) are **not yet captured** — they come from the schematic/demo package, not guesswork.

## Toolchain

**ESP-IDF 5.5** (installed at `C:\Users\13015\esp\v5.5\esp-idf`), C/C++. Chosen over Arduino/PlatformIO because TLS + streaming HTTP + audio codecs + PSRAM tuning are all first-class in IDF, and Espressif's `esp_codec_dev` covers ES8311/ES7210 directly.

## The big architectural fact: what does not port

Bookworm's Core is .NET. There is no .NET runtime for ESP32, so BookBook is a **re-implementation in C++, not a port**. The reusable asset is the *knowledge*: VA endpoints (`Bookworm/docs/va-endpoints.md`), the persona/tool schema, the memory model. The code is rewritten.

| Bookworm piece | BookBook equivalent |
|---|---|
| `VaLibraryClient` (HttpClient+cookies, 3-step login w/ CSRF) | `esp_http_client` + manual cookie jar; same handshake |
| `ClaudeBrain` (hand-rolled HTTP to `/v1/messages`) | Same, over TLS via `esp_http_client`; JSON via cJSON |
| `LibrarianOrchestrator` tool loop (max ~5 round trips) | Same loop in C++ |
| `AzureSpeechRecognizer` (SDK, push-to-talk) | Azure Speech **REST** short-audio endpoint (no SDK on ESP32) — see open decision |
| `SapiSpeechSynthesizer` | Cloud TTS (Azure neural voice REST) — SAPI doesn't exist here; on-device TTS quality is poor |
| `AzureBlobMemoryStore` (ETag concurrency) | Azure Blob REST with SAS token; same `memory.json` blob, so BookBook and Bookworm **share memory** |
| Windows Credential Manager | NVS (encrypted partition) or Wi-Fi provisioning + NVS |
| Push-to-talk button / WPF | Physical user button + audio earcons + LEDs |

## Proposed pipeline (half-duplex, same as Bookworm)

```
button down ─► record (ES7210, 16 kHz mono) ─► buffer in PSRAM
button up   ─► Azure STT REST ─► transcript
            ─► Brain (Claude, tool loop; VA + memory tools)
            ─► Azure TTS REST ─► stream/decode ─► ES8311 ─► speaker
```

- Half-duplex push-to-talk: no wake word, no AEC needed. Board's echo-cancel hardware is a later bonus, not a dependency.
- **Single-button UX** (must be fully audible): hold = talk; short press during reply = barge-in/cancel (mirrors Bookworm's barge-in). Earcons for: ready, listening, thinking (looping soft tick while waiting on network), error. Spoken short errors ("I can't reach the internet") — never raw API text (a lesson from Bookworm Phase 5).
- Wi-Fi provisioning must not need a screen: first-boot SoftAP + captive page (sighted helper does this once), credentials to NVS.

## Secrets

Per Bookworm's model: the end user only supplies their own VA login; the developer's Anthropic / Azure Speech / Azure Storage keys are seeded at flash time. On-device that means an NVS image generated by a script from the existing secrets, flash-encryption enabled for the release build. Keys never committed (`secrets/` is gitignored).

## Phased build order

| Phase | Goal |
|---|---|
| 0 — Bring-up | IDF project, capture pin map from schematic/demo, blink RGB LEDs, read button via TCA9555, Wi-Fi connect |
| 1 — Audio loop | Record from mics → play back on speaker (echo test, mirrors Bookworm Phase 2). Confirm levels, sample rates, amp enable |
| 2 — Speech | Azure STT + TTS over REST from the board; measure latency and accuracy on the real user's voice |
| 3 — VA client | Login handshake, search, bookshelf, request list on-device (validate against `raw` output from Bookworm.Console) |
| 4 — Brain | Claude tool loop + persona; memory blob via Azure REST. Live-test in dry-run first |
| 5 — Single-button UX + web config | Earcons, LEDs, barge-in, error handling, SoftAP/LAN configuration portal (Wi-Fi, VA login, keys, volume, gain). Wake word optional after this |
| 6 — Hardening | Enclosure/power, OTA updates, watchdogs, flash-encryption, real-user trial |

## Risks

- **TLS memory**: concurrent Anthropic + Azure + VA TLS sessions are heavy (~40 KB each in mbedTLS). Serialize connections, use PSRAM for buffers, trim mbedTLS config.
- **Latency stack**: STT → LLM (with tool calls) → TTS is several network round-trips per turn. Streaming TTS playback and a "thinking" earcon are needed so silence never reads as failure.
- **Claude payload size**: ReaderProfile / memory context must stay compact for RAM and token cost.
- **VA is an unofficial, unsanctioned integration** (same caveat as Bookworm): polite rate limiting, session re-auth on non-JSON responses.
- **Cert handling**: pin/bundle root CAs via `esp_crt_bundle`; needs correct time (RTC/SNTP) before TLS works.
- **Accessibility of setup**: Wi-Fi provisioning is the one step that can't be single-button.
- **Unconfirmed Bookworm gaps carry over**: download endpoint unknown (fine — BookBook does library *management*, not playback; whether it should also *play* books is an open product question).

## Decisions (owner, 2026-09-25)

1. **Scope**: library management + discovery only, as Bookworm. No audiobook playback (yet).
2. **STT/TTS**: Azure Speech REST, matching Bookworm.
3. **Power**: USB-C mains only; **no battery operation planned**. Optimise for fastest response: no sleep modes, Wi-Fi stays associated with power save off, TLS sessions to Anthropic/Azure/VA kept warm where practical, amp/codecs left powered.
4. **Wake word**: wanted later, not now. Push-to-talk stays the primary input. Design so it can be added: capture path must run continuously (not only while the button is held), and 16 MB flash / 8 MB PSRAM leave room for ESP-SR WakeNet (the reference project below uses it). Note the "fastest response, always powered" decision suits an always-listening wake word.
5. **Web-based configuration is required**: Wi-Fi selection, VA login, API keys, volume, mic gain (later wake phrase), served by the device itself (SoftAP captive portal on first boot / when no Wi-Fi, plus a page on the LAN afterwards). This replaces the earlier "Wi-Fi provisioning" idea and moves earlier in the plan (needed before the device can be handed over). Secrets go to NVS, never the web page source.

## Reference project

https://github.com/KMX415/waveshare-ai-speaker-assistant (MIT): ESP-IDF 5.5, same board, ESP-SR WakeNet wake word, streaming STT/LLM/TTS to OpenAI, browser-based setup portal, encrypted credential storage. Different cloud backends from BookBook, but a useful model for the wake word integration, the device portal, and board audio/AEC handling. Read it before Phases 2 and 5; copy ideas, and code only with its MIT notice kept.

## Conversation session model (wake word / pause detection)

Owner requirement: no wake word for every request (less conversational), but no continuously open Azure link.

- **Session start**: button (always available; also cancels a reply) or wake word (later, optional).
- **In a session**: on-device VAD (ESP-SR VADNet or energy-based to start) with a ~400 ms pre-roll ring buffer. Speech start -> record to PSRAM; trailing silence (~800-1000 ms, user-configurable) -> send that one utterance to Azure short-audio REST. No connection is held open between utterances.
- **After each reply**: earcon, then listen for a follow-up with no wake word. No speech for ~8-10 s -> session ends, back to idle. Timeouts configurable.
- **Half-duplex**: mic ignored while the device speaks (no voice barge-in without AEC); button barge-in remains. Short guard delay after TTS ends.
- **False-trigger control**: minimum speech duration before sending; short follow-up window.
- **Privacy statement to keep true**: no audio leaves the device outside an active session.

## Development without the board

Hardware arrives in a few days. Board IO sits behind `board.h`, so networking, Azure STT/TTS (fed from WAV files), VA client, Claude loop, memory and the web config portal can be developed on any ESP32-S3. Check the spare boards' PSRAM (N16R8 / N8R2 / none) before relying on them: TLS plus audio buffers need PSRAM.

## Bookworm's status (owner, 2026-09-26)

Bookworm was the **development version** of BookBook. It will either be retired or brought up to the BookBook
standard. BookBook is the reference now: where the two differ, BookBook's behaviour wins, and compatibility with
Bookworm's file format is a convenience, not a requirement. Some choices made only to stay compatible could be
revisited once Bookworm is retired or updated: a favourite book is a rating of 4 or 5 (there is no separate flag,
and favourites that were never borrowed have no dates), and the On Hold list lives in its own blob
(`standby.json`) instead of inside `memory.json`.

BookBook additions on top of Bookworm's design: practice mode; the standby (save-for-later) list; the authors and
books lists that fill themselves from bookshelf adds; verified removal of authors and books from those lists;
baked-in program settings with only the member's environment editable; touch-pad push-to-talk.
